# Decisions and open questions

Use this file to distinguish decisions the project owner has made from technical options to test. Add a date, reason, and impact when a proposal becomes a decision. Do not silently change the confirmed game pillars.

## Confirmed decisions

| ID | Decision | Reason and impact |
| --- | --- | --- |
| D-001 | Build a 3D online cooperative first-person shooter for 2–4 players. | This is the stated game vision. Systems must support independently controlled players working toward a shared mission. |
| D-002 | Players control movement and camera freely; the game is not a rail shooter. | Exploration and player agency are core to the experience. No automatic travel path or forced camera progression. |
| D-003 | Danger zones can start warnings, waves, ambushes, defense goals, and bosses over time. | Encounters should be reusable, but only one simple zone is needed in the first prototype. |
| D-004 | Use Unity 6000.6.5f1, URP, C#, and Git. Develop and test on macOS first; plan for Windows later. | Matches the current project and development environment. |
| D-005 | Build a narrow two-player first prototype before broader progression and content. | The first slice validates movement, online cooperation, shooting, an enemy, a danger zone, an objective, and extraction without implementing all future features at once. |
| D-006 | Use placeholders first and track third-party asset sources and licenses. Do not introduce paid services or assets without approval. | Keeps the early prototype inexpensive and its assets auditable. |
| D-007 | Use `main` for approved stable releases and `develop` for staging; branch features and normal fixes from `develop`, and urgent production hotfixes from `main`. | Separates release history from active development. The remote branch bootstrap was completed by PR #1. |
| D-008 | Route repository changes through PRs. Feature and normal fix PRs target `develop`; release PRs target `main`; production hotfixes return to `develop`. | Gives each change an explicit review and integration path. |
| D-009 | After bootstrap, do not commit or push directly to `main` or `develop`, force push protected branches, or let Codex merge PRs without explicit approval. Require automated checks once configured and human review where GitHub can enforce it. | Protects both branches and keeps merge authority with the project owner. |
| D-010 | For M1, use the installed Input System Player actions and a `CharacterController` with separate movement and camera scripts. Keep the player local and add ownership checks in the later online milestone. | Reuses the existing controls, gives collision and grounded jumping, and avoids adding a networking dependency before the online slice. |
| D-011 | 2026-10-11: For the owner-requested M2, build a local hitscan automatic rifle and resettable damage targets before the online foundation. R reloads from a finite reserve after a timed delay. | Proves the shooting loop in the existing map without installing network packages or services. Host authority and synchronization remain for a later milestone. |
| D-012 | 2026-10-12: Build local enemy AI and player combat as M3 before the online foundation. Use the installed AI Navigation package, the existing `IDamageable` seam, three placeholder enemies, and an R-key test reset after player death. | Proves detection, pathfinding, melee, rifle damage, and health in the graybox without adding networking. The reset is only for testing; teammate revive and host authority remain later work. |
| D-013 | 2026-10-12: Build two local danger zones as M4 before the online foundation. Use serialized scene components for per-zone warning, waves, delays, and NavMesh spawn markers; reuse `EnemyHealth.Died` for completion. | Proves reusable room encounters without a second health system or networking package. The encounter state resets with the test scene; shared host authority remains for the later online slice. |
| D-014 | 2026-10-12: Use NGO 2.13.3, Multiplayer Services Sessions 2.4.0 with Relay, and Multiplayer Play Mode 3.0.0 for the M5 join-code prototype. | Supported packages installed on Unity 6000.6.5f1. Private four-player sessions provide a small lobby and network connection without public matchmaking. Service use and billing must be reviewed in the Unity Dashboard before broader testing. |
| D-015 | 2026-10-12: Player owners control their CharacterController, camera, and immediate weapon cosmetics; the host owns ammunition, final damage and health, AI, target state, and danger-zone progression. | Local controls stay responsive while consequential gameplay decisions are shared. The host checks shot cadence, ammo, alive state, and aim plausibility, but owner movement remains trusted in this prototype. |
| D-016 | 2026-10-12: Join before match start; the host locks the session and loads the one test map. A host exit ends the session and returns clients to the menu. A dead player stays dead for the match; leaving and hosting again resets the test. | Keeps the first network loop bounded. Host migration, late joining, reconnect, revival, and advanced respawn await later milestones. |
| D-017 | 2026-10-17: Implement the first mission with three scene objectives (clear zones A/B and collect a sample), server-validated E interaction, and host-owned all-living-player extraction. | Demonstrates the complete cooperative loop in the existing explorable map without a generic quest framework. The 10-second extraction timer cancels when a required player leaves the area. Dead and disconnected players are excluded; if one drops out while everyone remaining is inside, the timer keeps its deadline. |
| D-018 | 2026-10-17: Score accepted shots, confirmed enemy hits, and unique enemy kills on the host; award each shared objective once to the team, then freeze an immutable result. Keep the Relay session for replay or lobby return while creating fresh match avatars. | Prevents client-authored score changes and stale state between matches. Defaults are 100/kill, 10/hit, 500/objective, zero success bonus. Because every run kills the same enemies, a successful extraction adds performance bonuses (4 per second under a 300-second par, up to 800 for team accuracy, up to 500 for the share of players who extracted), and success ranks B/A/S start at 3,400/3,900/4,300. Individual objective count credits direct sample collection. |
| D-019 | 2026-10-17: A mission that can no longer be completed ends in Failure with its reason instead of continuing. Waves fall back to open ground near blocked spawn markers and retry for up to 8 seconds before a zone stops. The host accepts client shots up to half a fire interval early. | Found in the M6 review: a player on a spawn marker stopped Zone A and left the session stuck, and strict shot pacing rejected about 20% of client shots under normal network jitter. The rifle's sustained rate is unchanged. |
| D-020 | 2026-10-17: For M9, not before: each mission starts beside a portal, which is the mission's way in and out. Before anyone crosses the visible gate in front of the spawn, the squad can step back through the portal and leave. Once a player crosses the gate, the portal closes until the squad gets the mission's key item. It then reopens, and the squad must bring the item back to it while under attack to earn the rewards; a squad that dies inside earns none. Rewards are shared by the team, and missions get harder with more players. | Gives each mission a commitment point and a tense return trip, and ties rewards to getting out. It grows out of the M6 extraction pad at the spawn, which already stays locked until the objectives are done. The portal belongs to the mission map, not the lobby. Reward amounts and difficulty scaling are part of the M9 progression work. |
| D-021 | 2026-10-17: M7 keeps weapon aiming, view motion, audio, and remote representation as cosmetic components around the existing rifle authority. Use an improved project-made placeholder until the owner approves a licensed external weapon and matching rigged hands. | Delivers responsive ADS and reload presentation without coupling damage or ammunition to a specific model or adding an unapproved asset. |
| D-022 | 2026-10-17: Give the current three-room mission map an abandoned research facility visual direction for M8A. This theme applies to this level; later levels may use different scenes and themes. | The owner approved the direction while noting that the game can contain multiple levels. Preserve the existing freely explorable layout, encounters, mission, and extraction. The owner separately approved the free Quaternius modular sci-fi pack and Poly Haven Metal Plate texture; see `ASSET_LICENSES.md`. |
| D-023 | 2026-10-18: Keep M8B impacts, enemy reactions, audio, and music as presentation driven by the existing host-authoritative shot, health, encounter, and mission state. Play music locally on each client. | Combat numbers, ammunition, AI, and mission outcomes stay in their established systems; only compact cosmetic shot and enemy-action events are sent. New third-party audio requires owner approval and license logging before import. |
| D-024 | 2026-10-23: Implement the later M9 brief's local per-player XP, levels, two cosmetic unlocks, host-selected Normal/Hard difficulty, and modest Zone B replay variation on top of the existing authoritative results. | Local versioned saves keep each computer's progression without adding an account backend. Completion rewards go only to living extractors; connected non-extractors receive reduced combat XP. An owner decision is pending on whether D-020's portal and team-reward plan is deferred beyond this PR; this implementation leaves the existing extraction layout intact. |

## Questions to resolve at the relevant milestone

1. How should the existing Interact action be used in the eventual mission loop? Resolved in M6 (D-017): E collects the research sample after the host checks range and line of sight.
2. What movement replication and validation model gives responsive controls while preserving host authority over consequential state? (M5/M6)
3. Does the M2 hitscan rifle's eight rounds per second, 30-round magazine, 90-round reserve, and 1.6-second reload feel right in human play testing? (Before networked combat)
4. What should happen when the host leaves: end the match, allow reconnect, or migrate host state? Decided for the prototype in D-016: the session ends and clients return to the menu. Reconnect or host migration remain options for later. (M8)
5. How are players invited or matched beyond the first join-code flow? (After M8)
6. What concrete scoring, rewards, progression, and retention systems should follow a proven mission loop? M6 added per-mission scoring and ranks (D-018). The later M9 brief adds local XP and cosmetics (D-024). Confirm whether D-020's portal and team rewards belong in a later milestone.
7. What online service setup and usage terms apply before enabling external services? (M5)
8. Does the GitHub repository plan and reviewer roster support enforceable required human approvals on both protected branches? As of 2026-10-17, both rulesets require a PR and resolved conversations but 0 approvals, because the owner is the only collaborator and cannot approve their own PRs. Raise it to one approval when a second reviewer with write access joins.
9. After a mission, should the whole squad return to a shared lobby without the join code, whichever player chooses to leave? The owner expects this (2026-10-17). Today only the host's **Return to Lobby** keeps the session; **Leave Session** exits to the main menu. (Not yet scheduled; see [ROADMAP.md](ROADMAP.md))
